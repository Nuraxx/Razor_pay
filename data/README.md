# Synthetic Recovery Dataset

## ⚠️ This data is synthetic

Every row in `data/raw/` and `data/processed/` is generated by
`generate_synthetic_dataset.py` from a hand-designed probabilistic model. **It
is not derived from, sampled from, or fitted to real Razorpay transactions or
real customer behavior.** Recovery rates, timing patterns, and archetype
proportions in this dataset reflect assumptions the author chose while
building a *training/evaluation harness* for the downstream model/policy
layer — they are not a claim
about how real Razorpay subscription customers behave, and must not be cited
as such. See "Limitations" below.

## Purpose

The downstream model/policy layer trains a model to predict, for a
subscription that just failed an `insufficient_fund` payment, the
probability of recovery within 14 days at a handful of candidate retry
times. That needs a labeled dataset. This generator builds it —
deterministically, reproducibly, and without letting the label depend on
any single visible feature or leak information from the future.

```
Razorpay Subscriptions -> insufficient_fund failures -> candidate retry times -> P(recovered within 14d)
```

No model is trained by this generator (see its own scope note at the top of
`generate_synthetic_dataset.py`) — this is the dataset that training
consumes.

## Regenerate the dataset

```bash
./venv/bin/python data/generate_synthetic_dataset.py
```

Optional flags: `--seed 42` (default), `--n-subscriptions 1500` (default,
increased from 200 — final pre-submission audit, "improve Model B using more
synthetic data only"; see §16d in the top-level README for the before/after
comparison this produced), `--output-dir data` (default). The command prints
a dataset summary and a validation report, and exits non-zero if validation
fails.

## Reproducibility

Every random draw in the generator goes through one `numpy.random.Generator`
seeded once, at the top of `generate_dataset(seed, n_subscriptions)` — no
code path uses the stdlib `random` module, pandas' own sampling, or
`datetime.now()`. All dates are computed relative to a fixed constant,
`EXTRACTION_DATE = 2026-06-30`, defined in the script. Consequences:

- Running the command above twice, with the same seed, produces
  byte-identical CSVs — verified in `tests/test_dataset_generation.py::test_reproducibility_same_seed_produces_identical_data`.
- This holds regardless of what day it's actually run, since no real
  wall-clock time is ever read.
- A different `--seed` produces a different (but still internally valid)
  dataset — useful for generating held-out re-runs later without touching
  the code.

## Schema

### `data/raw/subscriptions.csv` (one row per subscription)

| column | meaning |
|---|---|
| `subscription_id` | `sub_SYNxxxxx` |
| `plan_tier` | `mobile` (₹79–199) / `mid` (₹299–499) / `premium` (₹649–999) / `saas` (₹1,000–5,000) |
| `monthly_amount` | the tier's billed amount, in ₹ |
| `signup_date` | fixed, relative to `EXTRACTION_DATE` |
| `primary_instrument` | `credit_card` / `debit_card` / `upi_autopay` / `netbanking` |
| `city_tier` | `tier_1` / `tier_2` / `tier_3` |
| `tenure_days` | tenure **as of `EXTRACTION_DATE`** — see "Leakage prevention," this is *not* used as a model feature |
| `archetype` | **hidden, generation-only** — see below. Present here, absent from `data/processed/*.csv` |
| `split` | `train` / `validation` / `test` — assigned per-subscription before any events are generated |

### `data/raw/failure_events.csv` (one row per failed `insufficient_fund` charge)

`event_id`, `subscription_id`, `failure_timestamp`, `day_of_month`,
`days_to_nearest_payday_window`, `error_reason` (always
`insufficient_fund` — by design, see scope note), `amount`, `prior_if_failure_count`,
`prior_if_self_resolved_rate`, `tenure_days` (**as of this failure** — the
leakage-safe version), plus the exogenous/distractor columns below.

Exogenous (systemic, generated independently of archetype — see
"Leakage prevention"): `bank_network_conditions`, `issuing_bank_downtime_flag`,
`network_latency_bucket`, `is_month_end_settlement_rush`.

Distractors (sanity-check only — must NOT meaningfully predict recovery):
`app_version`, `device_build`, `ui_theme`.

### `data/raw/retry_candidates.csv` (five rows per failure event)

`retry_candidate_id`, `event_id`, `subscription_id`, `candidate_type`
(`immediate` / `plus_1_day_morning` / `payday_window` / `plus_3_days` /
`month_end_window`), `candidate_datetime`, `offset_hours_from_failure`,
`day_of_week`, `is_payday_aligned`, `is_month_end_aligned`.

This table is descriptive only — no outcome or label is attached to a
candidate. Which retry time is actually best is the downstream
model/policy layer's question, not this generator's; retry-time selection
is explicitly out of scope here.

### `data/raw/recovery_outcomes.csv` (one row per failure event)

`event_id`, `subscription_id`, `recovered_within_14d`, `recovered_at`
(null iff not recovered), `recovered_via` (`auto_retry` /
`customer_self_serve` / `none`), `final_amount_recovered` (never exceeds
the failed `amount`).

### `data/processed/{train,validation,test}.csv` (model-ready)

One row per failure event: every `failure_events` column, joined with its
`recovery_outcomes` row and a leakage-safe subset of subscription
attributes (`plan_tier`, `monthly_amount`, `primary_instrument`,
`city_tier`, `signup_date`). **`archetype` and `split` are dropped here** —
see "Hidden archetype" and "Leakage prevention."

## Hidden archetype methodology

Every subscription is secretly assigned one of four behavioral archetypes
at generation time, in these approximate proportions (sampled, not forced
exact — see "Reproducibility"):

| archetype | proportion | recovery tendency |
|---|---|---|
| `reliable` | 50% | recovers fast and often — a one-off blip |
| `cash_strapped_cyclical` | 25% | recovers, but needs to be near a payday window |
| `chronic_struggler` | 15% | recovers roughly half the time, unpredictably |
| `quiet_canceller` | 10% | rarely recovers — mentally already checked out |

The archetype drives the **generation mechanism** (failure frequency, gap
between repeat failures, payday sensitivity, recovery speed, and the
`recovered_via` channel) — never the model's inputs. The model only ever
sees the *effects* of archetype through legitimate observable proxies:
timing (`days_to_nearest_payday_window`), history
(`prior_if_failure_count`, `prior_if_self_resolved_rate`), and tenure. This
is by design: a good model has to learn the interaction between these
proxies and outcome, not read a label off a hidden field. Concretely, the
payday effect is close to flat when you pool all archetypes (~0.68
recovery rate across every proximity bucket) but strongly monotonic *within*
`cash_strapped_cyclical` alone (0.90 near payday -> 0.70 far from it) — the
signal is real but conditional, exactly the kind of interaction a
feature-only model has to discover rather than read off one column.

`archetype` is written to `data/raw/subscriptions.csv` (clearly labeled
"generation-only") and is asserted absent from every `data/processed/*.csv`
file, both in `validate_dataset()` and in
`tests/test_dataset_generation.py::test_hidden_archetype_excluded_from_processed_datasets`.

## Leakage prevention

1. **Split before generation.** `subscriptions.csv` gets its `train` /
   `validation` / `test` label the moment it's created — before a single
   failure event, retry candidate, or outcome exists. Every row derived
   from a subscription inherits that one split; a subscription can never
   straddle two splits (`test_zero_subscription_overlap_between_splits`,
   `test_a_subscriptions_full_event_history_stays_in_one_split`).
2. **`prior_if_failure_count` / `prior_if_self_resolved_rate` are causal.**
   Failure events for a subscription are generated in chronological order,
   in a single pass, and these two columns are computed from *only the
   events generated so far for that subscription* before the current
   event's outcome is drawn. The first failure of any subscription always
   has `prior_if_failure_count == 0` and a missing (`NaN`)
   `prior_if_self_resolved_rate` — there is nothing earlier to compute it
   from, and the generator does not invent a value.
3. **`subscriptions.tenure_days` never reaches the model.** That column is
   tenure *as of `EXTRACTION_DATE`* — if a subscription is still around at
   that fixed future point, it implicitly means it didn't churn, which
   leaks the very thing a churn-adjacent model would be trying to predict.
   `data/processed/*.csv` instead carries `failure_events.tenure_days`,
   tenure *as of that specific failure* — the only version that was
   actually knowable at decision time.
4. **No cross-subscription statistics are fit anywhere in this generator.**
   There is no scaling, encoding, or normalization step (that's the
   downstream model/policy layer's job), so there is no "fit on train, leak
   into test" risk to guard against yet.

## Probabilistic label-generation methodology

`recovered_within_14d` is **not** a deterministic function of any one
column. Each failure event's recovery probability is built as a logit,
combined from several weak-to-moderate terms plus substantial noise, then
passed through a sigmoid and sampled:

```
logit = archetype_base_logit                                   # hidden
      + payday_sensitivity[archetype] * proximity_to_payday     # hidden x visible interaction
      + 1.0 * prior_if_self_resolved_rate        (if known)     # visible, causal
      + amount_penalty(amount)                                  # visible
      + exogenous_penalties(bank/downtime/latency/month-end)    # visible, archetype-independent
      + tenure_bonus(tenure_at_failure)                         # visible
      + Normal(0, 0.9)                                          # noise

p = clip(sigmoid(logit), 0.02, 0.98)
recovered_within_14d ~ Bernoulli(p)
```

The noise term (`NOISE_STD = 0.9` on the logit scale) is the main lever
keeping this learnable-but-imperfect: it's large relative to most individual
term sizes, so no single visible column comes close to determining the
label deterministically (`test_class_balance_is_not_degenerate`). A model
that combines several of the visible proxy signals should land somewhere
well short of perfect separation — the intent, sized off these same effect
magnitudes, is roughly AUC 0.75–0.85 for a well-fit model. **This generator
does not train a model and has not empirically measured this** — that
verification is the downstream model layer's job; treat the range as a
design target, not a result.

The three distractor columns (`app_version`, `device_build`, `ui_theme`)
are drawn independently and never enter the logit formula above — that's a
structural guarantee, not a statistical one. At n≈200/313 the per-category
recovery rate still wobbles (`ui_theme` spans ~0.61–0.78 across its three
values in the seed-42 run), which is ordinary finite-sample noise, not a
real effect. That wobble is a feature, not a bug: it's exactly the kind of
spurious signal a feature-importance check on the real model should learn
to ignore.

`recovered_at` (when recovered) is drawn from an exponential distribution
whose scale depends on archetype (`reliable` resolves in ~1–2 days on
average, `quiet_canceller` — on the rare occasion it resolves at all —
takes closer to the full 14), clipped to `(0, 14]` days after
`failure_timestamp`. `recovered_via` is drawn from an archetype-specific
mix of `auto_retry` / `customer_self_serve`. `final_amount_recovered` is
the full `amount` in ~90% of recoveries and a small (5–15%) haircut in the
rest, and is `0` whenever `recovered_within_14d` is `False`.

## Limitations

- **Not real behavior.** See the disclaimer at the top of this file. Every
  probability, rate, and proportion here is an authored assumption.
- **Coefficients are hand-picked, not fit.** The logit weights above were
  chosen for plausible relative direction and magnitude, not calibrated
  against any real dataset.
- **AUC target is unverified.** No model has been trained against this data
  by this generator; the "0.75–0.85" figure is a design intent based on the
  chosen effect sizes and noise level, not a measured result.
- **Default increased from 200 to 1500 subscriptions** (final pre-submission
  audit — ~2,344 failure events at the current default, up from ~300).
  Regenerating changes every downstream number, exactly as this paragraph
  originally warned it would: `data/raw/*.csv`, `data/processed/*.csv`, and
  every model artifact trained from them must all be regenerated/retrained
  together (see the top-level README's §16d) — an artifact trained against
  one `--n-subscriptions` value and evaluated against data regenerated at a
  different one would silently compare two different populations. Still
  reproducible and byte-identical for a given seed; no longer small enough
  to review as a full diff (the original 200-subscription rationale for
  that property), a deliberate tradeoff made to give the model more signal.
- **Still synthetic, regardless of size.** More rows does not change the
  disclaimer at the top of this file — every number remains an authored
  assumption from a hand-designed probabilistic model, not real Razorpay
  behavior. A larger N makes internal signal-to-noise/statistical-power
  arguments more reliable; it does not make the data any less synthetic.
- **Only one `error_reason`.** This generator only generates
  `insufficient_fund` failures, by design — `hard_decline` /
  `customer_cancelled` failures (already classifiable by the deterministic
  classifier) are not represented here.
- **Retry candidates carry no outcome.** `retry_candidates.csv` is
  descriptive (candidate times only) — it does not say which candidate
  would have recovered the payment. Building that signal is retry-time
  selection, explicitly out of scope for this generator.
